# 订单块 × 趋势 × 动量 × ATR：构建可验证的量化回测框架

结合你目前的 CTA 量化研究台 `cta-path-a`，我建议不要把订单块（Order Block，OB）简单地做成一个新的买卖指标，而是将它作为**交易信号引擎的一部分，通过严格的历史回测，验证它能否在趋势、动量、波动率和风险控制系统之外，提供独立的超额收益。**

真正需要回答的不是“订单块看起来准不准”，而是以下五个问题：

1. **信号有效性：** 价格回到订单块区域后，是否比普通回踩更容易产生有利的价格变化？
2. **市场适应性：** 订单块在趋势行情、震荡行情和高波动行情中，表现是否存在显著差异？
3. **组合增量：** 在已有趋势和动量策略上增加订单块，能否提高收益、降低回撤，或改善风险调整后收益？
4. **交易成本：** 加入手续费、滑点、跳空和止损成交偏差后，策略是否仍然有效？
5. **样本外稳定性：** 在没有参与参数选择的历史区间，以及不同商品品种上，优势是否仍然存在？

我建议将整个系统分为六层：

这里需要特别强调：上面的动量可视化只是基础概念示意，不代表订单块策略的收益关系。订单块回测的核心，是将市场结构、信号生成、交易执行和风险管理分离，并对每一层单独验证。

## 一、先确定研究架构：六层系统

| 层级 | 模块 | 主要职责 | 关键输出 |
| --- | --- | --- | --- |
| L1 | 行情与数据层 | 处理 OHLCV、成交量、持仓量、合约换月和交易日历 | 标准化行情数据 |
| L2 | 市场结构层 | 识别订单块、结构突破、回踩、失效和流动性扫荡 | 订单块事件及区域 |
| L3 | 过滤与评分层 | 识别趋势、动量、波动率及市场状态 | 多因子信号分数 |
| L4 | 交易执行层 | 入场、止损、止盈、持仓、滑点和手续费 | 逐笔交易记录 |
| L5 | 组合与风险层 | 仓位计算、总风险限额、品种相关性和资金管理 | 组合净值及风险暴露 |
| L6 | 评估与迭代层 | 多模型对比、样本外验证、参数稳定性和增量收益评估 | 研究报告及模型晋级结论 |

**最重要的工程原则：信号生成、交易执行和绩效评价必须分开。**

例如，订单块识别器只负责回答“什么时间、什么价格区域出现了符合定义的订单块”，不应直接决定最终仓位；趋势过滤器只负责判断趋势环境，不应偷偷修改订单块的历史识别结果。

这样才能知道策略为什么赚钱、为什么亏钱，以及新增一个模块究竟贡献了什么。

# 二、第一步：建立可回测的订单块定义

订单块没有唯一公认的数学定义。不同交易者对订单块的识别规则不同，因此必须先将主观图形转化为可重复执行的算法。

我建议第一版采用：

**市场结构突破 + 最后反向 K 线 + 回踩确认。**

先研究这个版本，再扩展到流动性扫荡、成交量确认和多周期订单块。

## 2.1 定义多头订单块

假设使用日线识别市场结构，在某一根 K 线上出现向上结构突破。

定义：

- `BOS`：向上突破此前已经确认的摆动高点。
- `OB`：突破发生前，最近一根符合条件的阴线。
- `OB_H`：该阴线最高价。
- `OB_L`：该阴线最低价。
- `OB_M`：订单块区域中点。
- `Retest`：价格在订单块被确认之后，首次或规定次数内重新进入区域。
- `Invalidation`：价格有效跌破订单块失效边界。

第一版可以将多头订单块定义为：

1. 使用固定参数识别已经确认的摆动高点。
2. 收盘价突破该高点，形成向上 BOS。
3. 在突破之前的固定回看窗口中，寻找最近一根阴线。
4. 将该阴线的高低价定义为订单块区域。
5. 订单块只有在突破信号实际可观察之后才能生效。
6. 价格随后回踩订单块，才允许产生交易信号。
7. 价格有效跌破失效边界后，该订单块不再用于新交易。

空头订单块反向处理。

### 这里有三个容易导致回测失真的问题

**问题一：未来函数。**

如果使用后面几根 K 线才能确认的摆动高点，却在摆动高点出现当日就交易，回测将获得现实中不可能取得的信息。

正确做法是：摆动高点形成于时间 `t`，但只有到 `t+k` 确认条件满足时，才允许策略使用它。

**问题二：订单块时间穿越。**

假设某根阴线在 10:00 出现，10:30 才发生向上突破，那么订单块最早只能在突破信息实际可用之后生效。不能利用后来发生的突破，提前在 10:00 生成信号。

**问题三：订单块失效与回测结束时间不一致。**

不能在回测结束时，倒过来只挑选后来产生反弹的区域作为订单块。所有符合规则的订单块都必须保留，包括反弹失败、直接跌穿和始终未回踩的区域。

这三条决定了订单块策略有没有研究价值。图表上漂亮的订单块并不难找，难的是在不看未来的前提下提前识别它们。

## 三、第二步：把趋势、动量和 ATR 转换成独立模块

建议不要一开始就把所有指标混成一个综合评分。先逐个验证它们的作用，再测试组合。

### 3.1 趋势模块：决定是否顺势交易

第一版可以采用均线结构过滤：

$$
Trend_t =
\begin{cases}
+1,& Close_t>EMA_{50,t}\ \land\ EMA_{50,t}>EMA_{50,t-10}\\
-1,& Close_t

| 模型 | 趋势识别方法 | 主要目的 |
| --- | --- | --- |
| T1 | 收盘价与 EMA50 的相对位置 | 简单、容易复现 |
| T2 | EMA20、EMA50 的排列及斜率 | 识别趋势方向与持续性 |
| T3 | EMA 结构 + ADX | 避免在趋势强度不足时交易 |

注意，趋势过滤有可能减少交易次数，却不一定提高策略收益。它也可能错过震荡区间中订单块产生的有效反转。因此，必须比较净收益、回撤、盈亏比及交易数量，而不是只看胜率。

### 3.2 动量模块：决定价格是否具备延续性

动量不是简单地判断涨跌，而是判断价格变化的速度、方向及持续性。

建议测试以下三类指标。

**A. ROC 动量**

 $ROC_n(t)=\frac{Close_t}{Close_{t-n}}-1$

例如，测试 5、10、20 根 K 线的 ROC。

多头过滤条件可以设置为 ROC 大于零，空头则相反。

**B. MACD 动量**

观察 MACD 线与信号线的关系，以及柱体是否扩张。

它适合衡量趋势动量的变化，但与均线趋势过滤存在信息重叠，不能默认加入后就会提高收益。

**C. RSI 动量**

可以将 RSI 作为方向和动量强弱的辅助变量，例如观察 RSI 是否处于中性区间上方、是否持续增强。

不建议在第一版同时叠加 ROC、MACD、RSI 三种硬性过滤。指标越多，越容易产生参数过拟合。

我的建议是：**先用 ROC 作为主动量指标，再分别测试 MACD 和 RSI 是否能提供独立增量。**

### 3.3 ATR 模块：统一止损、仓位和波动率管理

ATR 是平均真实波幅，用来衡量近期价格波动。

真实波幅：

$$
TR_t=\max
\begin{cases}
High_t-Low_t\\
|High_t-Close_{t-1}|\\
|Low_t-Close_{t-1}|
\end{cases}
$$

采用 Wilder 平滑方法计算 ATR。

对于多头订单块，假设：

- 订单块下沿为 $OB_L$ ；
- 实际入场价为 $P_e$ ；
- 入场时 ATR 为 $ATR_e$ 。

止损可以设置为：

 $P_{stop}=OB_L-k\times ATR_e$

其中， $k$  是缓冲系数。

第一轮可以测试：

 $k\in\{0,\ 0.25,\ 0.5,\ 1.0\}$

这组参数的含义是：

- `0`：订单块下沿不增加 ATR 缓冲。
- `0.25`：增加较小缓冲。
- `0.5`：增加中等缓冲。
- `1.0`：增加较大缓冲。

空头订单块使用对称规则。

但不能简单地认定缓冲越大越好。缓冲过小容易被正常波动扫损，缓冲过大则会扩大单笔风险、减少可开仓手数，并可能降低资金利用效率。

还要测试另一种方案：不使用订单块边界止损，而是采用纯 ATR 止损。

 $P_{stop}=P_e-k\times ATR_e$

对多头而言，上式成立；空头方向反向计算。

**这两种止损应当作为不同实验组，不能把它们的收益混在一起。**

### 3.4 订单块质量评分：作为后续增量模块

在基础策略跑通后，再增加订单块质量评分。

可以考虑：

- BOS 的突破幅度。
- 突破时成交量相对于近期均值的变化。
- 订单块形成后，价格是否快速离开区域。
- 订单块宽度相对于 ATR 的比例。
- 回踩次数及订单块是否已被部分消耗。
- 订单块与高周期趋势是否一致。

例如，订单块宽度：

 $OBWidth=\frac{OB_H-OB_L}{ATR_e}$

这个指标可以帮助区分过宽和过窄的区域。

但是，不要预设“突破幅度越大越好”或“成交量越大越好”。这些都应作为待检验假设，而不是预先确定的事实。

# 四、第三步：设计多模型对照实验

这是整套研究中最重要的一环。

你需要建立一个统一的实验矩阵，让每个模型使用相同的数据区间、交易成本、资金规模和风险预算。

## 4.1 建立基础模型组

建议按照以下顺序推进。

| 编号 | 模型 | 订单块 | 趋势过滤 | 动量过滤 | ATR 风险管理 | 研究目的 |
| --- | --- | --- | --- | --- | --- | --- |
| M0 | 基准模型 | 否 | 否 | 否 | 否 | 建立基准 |
| M1 | 纯订单块 | 是 | 否 | 否 | 固定风险止损 | 验证订单块是否有效 |
| M2 | 趋势模型 | 否 | 是 | 否 | ATR | 验证趋势策略基准 |
| M3 | 趋势 + 动量 | 否 | 是 | 是 | ATR | 验证动量增量 |
| M4 | 订单块 + 趋势 | 是 | 是 | 否 | ATR | 验证趋势是否改善订单块 |
| M5 | 订单块 + 动量 | 是 | 否 | 是 | ATR | 验证动量是否改善订单块 |
| M6 | 订单块 + 趋势 + 动量 | 是 | 是 | 是 | ATR | 验证组合收益 |
| M7 | M6 + 订单块质量评分 | 是 | 是 | 是 | ATR | 验证质量评分增量 |
| M8 | M6 + 自适应止损 | 是 | 是 | 是 | 动态 ATR | 验证止损方式的增量 |

其中，M0 应根据研究目的分别设置两种基准：

1. 空仓基准：用于检查交易策略是否创造正收益。
2. 简单趋势基准：例如只采用 EMA 趋势方向、固定风险预算和相同交易成本，用于判断复杂订单块模型是否优于更简单的方法。

M1 使用固定风险止损，并不是说它在实际交易中应当忽略 ATR，而是为了区分订单块信号本身的有效性和风险管理带来的改善。

如果 M1 表现不佳，但 M6 表现良好，还需要进一步判断：收益究竟来自订单块、趋势、动量，还是组合中的其他因素。

## 4.2 使用消融实验识别真实贡献

在 M6 基础上逐项删除模块：

| 实验 | 模型变化 | 要回答的问题 |
| --- | --- | --- |
| A1 | 完整模型去掉订单块 | 订单块是否提供独立价值？ |
| A2 | 完整模型去掉趋势过滤 | 趋势过滤是否有帮助？ |
| A3 | 完整模型去掉动量过滤 | 动量过滤是否有帮助？ |
| A4 | 完整模型去掉 ATR 止损 | ATR 是否改善风险收益？ |
| A5 | 完整模型去掉订单块质量评分 | 评分是否值得增加复杂度？ |

举例来说：

假设完整模型 M6 的样本外年化收益为 12%，去掉订单块后为 10%。

那么可以说，在这个实验设定下，包含订单块的模型年化收益高出 2 个百分点。

**但这不能直接证明订单块贡献了 2 个百分点的可持续超额收益。** 两个模型的交易次数、持仓时间、风险暴露可能不同，而且这仍然是一个特定样本中的结果。

要得出更可靠的结论，需要继续比较风险匹配后的收益、配对交易事件、交易成本敏感性，以及不同市场状态下的表现。

# 五、第四步：制定严格的回测执行规则

订单块策略特别容易出现一种情况：信号识别是正确的，但交易模拟方式过于理想化，最终得到虚假的盈利优势。

因此，执行引擎需要明确以下规则。

## 5.1 信号产生时间与成交时间分离

假设使用日线数据：

- 第 1 天收盘，确认市场结构突破。
- 第 1 天收盘后，识别订单块。
- 第 2 天及以后，等待价格回踩。
- 第 5 天价格进入订单块区域，产生候选入场信号。
- 第 6 天开盘，按照预先规定的执行规则成交。

这里的具体日期只是示例。

不能在第 5 天收盘后才确认回踩，却又假定自己在第 5 天的最低价买入。

对于日线回测，第一版应采用**收盘生成信号、下一交易日开盘成交**的规则。待基础版本稳定后，再使用 5 分钟或更细粒度的数据模拟限价单、止损单及盘中成交。

## 5.2 限价单如何模拟

如果价格回踩订单块后，你希望在订单块中点买入，不能简单地认为价格触及中点就一定成交。

应当区分：

1. **触价：** K 线最低价低于或等于限价。
2. **成交假设：** 价格触及限价后，是否假设全部成交。
3. **成交优先级：** 如果开盘已经跳过限价，如何处理。
4. **流动性约束：** 是否考虑盘口深度、排队和部分成交。
5. **成交成本：** 成交价格是否包含滑点。

如果只有 OHLCV 数据，无法精确还原真实盘口排队情况。因此，限价成交率只能通过明确的模拟规则近似，不能将所有触价都当作无条件成交。

可采用三组执行情景：

| 情景 | 成交假设 | 用途 |
| --- | --- | --- |
| E1 | 触价即成交 | 较乐观的基准 |
| E2 | 触价后增加成交确认条件 | 中性情景 |
| E3 | 未满足更严格的成交条件则不成交，并增加滑点 | 保守压力测试 |

E1 不宜作为最终策略有效性的唯一依据。

## 5.3 同一根 K 线同时触及止盈和止损怎么办？

例如，一根日线的最高价触及止盈价，最低价又跌破止损价，但你没有分钟级数据，无法知道先发生哪一个。

不能直接选择对策略更有利的成交顺序。

建议：

- 基础测试中，采用对策略不利的成交顺序。
- 使用更低周期数据，尽可能还原触发顺序。
- 对无法确定顺序的交易，记录其占比并做敏感性分析。

如果策略只有在乐观成交假设下才赚钱，就不应晋级。

## 5.4 国内商品期货必须处理的成本

对于郑棉 CF2701 等国内商品期货，至少需要建模：

- 开仓手续费。
- 平仓手续费及平今仓差异。
- 买卖方向的滑点。
- 合约乘数。
- 保证金占用。
- 涨跌停板和无法成交风险。
- 夜盘与日盘交易时段。
- 主力合约切换和到期处理。
- 跨合约移仓的交易成本。

手续费、保证金比例和交易规则应来自对应交易所、期货公司及历史规则资料，并按日期维护，不能将今天的费率直接套用到所有历史年份。

连续合约可以用于趋势和订单块的初步研究，但正式绩效必须建立在可执行的实际合约交易路径上。尤其是换月期间，不能把连续合约的回溯调整价格当成真实成交价格。

对于成本建模，可以参考 VectorBT 官方回测与交易成本文档

 和 Backtrader 滑点说明

。这两类框架都提供了模拟交易成本或成交执行的相关能力，但具体期货规则仍需自行实现和验证。

# 六、第五步：建立统一的绩效评估体系

不要只看胜率、总收益或盈亏比中的任何一个指标。

我建议把绩效指标分为五组。

## 6.1 收益能力

| 指标 | 计算或含义 | 主要用途 |
| --- | --- | --- |
| 累计净收益 | 扣除交易成本后的累计盈亏 | 观察总体结果 |
| 年化收益率 | 根据净值和实际时间计算 | 比较不同测试区间 |
| 单笔期望收益 | 每笔交易净收益的平均值 | 判断单笔交易是否具有正期望 |
| 盈亏比 | 平均盈利 ÷ 平均亏损绝对值 | 评估盈亏结构 |
| 资金利用效率 | 净收益相对于实际风险资本或资金占用 | 比较资金效率 |

单笔交易的数学期望为：

 $E=p_w\bar W-(1-p_w)\bar L$

其中：

- $p_w$ ：盈利交易比例。
- $\bar W$ ：平均盈利金额。
- $\bar L$ ：平均亏损金额的绝对值。

例如，假设胜率为 40%，平均盈利为 3R，平均亏损为 1R：

 $E=0.4\times3-0.6\times1=0.6R$

这意味着理论上的单笔毛期望为 0.6R，尚未扣除交易成本。

这个例子只是数学演示，并不是订单块策略的实测结果。

## 6.2 风险控制

必须至少记录：

- 最大回撤。
- 年化波动率。
- Sharpe Ratio。
- Sortino Ratio。
- Calmar Ratio。
- 最大连续亏损次数。
- 最大单笔亏损。
- 最大资金占用。
- 保证金占用峰值。
- 不同市场状态下的回撤。

其中，最大回撤尤其重要。

如果订单块模型收益较高，但回撤也大幅上升，就需要进一步比较单位回撤对应的收益，而不是直接判定新模型更优秀。

## 6.3 交易质量

每笔交易都应记录：

| 字段 | 作用 |
| --- | --- |
| 订单块 ID | 确定交易对应的订单块 |
| 订单块形成时间 | 检查信号是否存在未来函数 |
| 结构突破时间 | 确认订单块何时有效 |
| 回踩时间 | 计算信号到入场的等待时间 |
| 入场价格 | 评估成交质量 |
| 初始止损 | 计算初始风险 |
| 实际止损 | 评估止损偏差 |
| 最大有利变动 MFE | 观察交易期间最大浮盈 |
| 最大不利变动 MAE | 观察交易期间最大浮亏 |
| 持仓时间 | 判断策略的资金效率 |
| 毛盈亏 | 交易成本前的收益 |
| 手续费和滑点 | 交易成本分解 |
| 净盈亏 | 实际模拟交易结果 |

这里的 MFE 和 MAE 非常有价值。

例如，如果多数盈利交易在入场后先出现较大浮亏，再逐渐反弹，那么当前止损可能过紧；如果大部分交易入场后立即顺势，却因为固定止盈过早离场，那么可能需要研究移动止盈。

但这些结论必须从逐笔交易数据中验证，不能仅凭几张图表得出。

## 6.4 统计可靠性

建议额外统计：

- 交易笔数及有效独立交易事件数量。
- 单笔期望收益的置信区间。
- 不同年份的收益分布。
- 不同品种的收益分布。
- 不同趋势状态下的表现。
- 参数微调后的表现变化。
- 对交易顺序或收益序列进行重采样后的回撤分布。

要特别注意：100 笔高度相关的交易，并不等于 100 个独立样本。

如果某一轮行情中，策略连续触发了大量相似订单块，这些交易可能受到同一个市场事件影响。计算置信区间时，应考虑时间相关性，而不是机械地将每笔交易视为独立观察值。

## 6.5 成本敏感性

建议至少比较以下情景：

| 测试组 | 交易成本设定 | 研究目的 |
| --- | --- | --- |
| C0 | 零成本 | 了解理论信号表现，不用于最终晋级 |
| C1 | 基准手续费与滑点 | 评估常规情景 |
| C2 | 基准滑点的 1.5 倍 | 测试一般成本恶化 |
| C3 | 基准滑点的 2 倍 | 测试较严重成本冲击 |
| C4 | 更严格的限价成交规则 | 测试成交假设依赖程度 |

以上倍数是建议的压力测试档位，并非对实际滑点的预测。

**如果加入订单块之后，毛收益提高，但净收益下降，那么新增模块很可能没有经济价值。**

# 七、第六步：怎样衡量订单块的增量效益？

这是你要重点建立的研究能力。

增量效益不是简单比较两个模型的累计收益，而是研究：在其他条件尽量一致的情况下，新增模块是否改善了结果。

## 7.1 第一层：比较总体绩效

假设测试后得到以下结果。

注意：以下数据是演示用的假设数据，不是真实回测结果。

| 指标 | 模型 A：趋势 + 动量 + ATR | 模型 B：订单块 + 趋势 + 动量 + ATR |
| --- | --- | --- |
| 样本外年化收益 | 8% | 10% |
| 最大回撤 | 12% | 10% |
| Sharpe Ratio | 0.75 | 0.95 |
| 交易次数 | 150 | 100 |
| 胜率 | 42% | 48% |
| 平均持仓时间 | 4 天 | 5 天 |
| 年化换手率 | 18 倍 | 12 倍 |

在这个假设例子中，B 的年化收益高出 2 个百分点，最大回撤降低 2 个百分点。

但仍然不能马上下结论。

因为 B 的交易次数更少、持仓时间更长、换手率更低，收益差异可能来自更少的交易成本，也可能来自风险暴露差异，或者仅仅来自特定样本。

因此还需要下面几层分析。

## 7.2 第二层：匹配风险预算

至少使用两种比较方法。

**方法 A：相同风险预算。**

让两个模型的单笔风险占净值比例一致，例如都以 0.5% 为单笔初始风险上限。

这样可以减少仓位大小差异对绩效比较的影响。

**方法 B：相同组合风险。**

根据各模型的实际波动率或组合风险，将策略调整到相近的风险水平，再比较净收益、回撤和风险调整后收益。

需要注意，ATR 止损并不保证实际亏损等于预设风险。跳空、涨跌停及滑点都可能使实际损失超过计划值。

## 7.3 第三层：配对比较订单块事件

这一步能更直接地回答订单块有没有预测价值。

对于每个符合规则的订单块事件：

1. 记录订单块确认时间。
2. 记录首次有效回踩时间。
3. 记录回踩后的价格路径。
4. 计算未来 1、3、5、10 根 K 线的收益。
5. 计算期间最大有利变动和最大不利变动。
6. 选择相同市场状态下的普通回踩事件作为对照。
7. 比较订单块事件与对照事件的收益分布。

例如，订单块事件和普通回踩事件都发生在上涨趋势中，且波动率相近。

如果订单块回踩后的平均净收益、正收益比例或风险调整后收益持续高于普通回踩，才有证据支持订单块具备额外的信息价值。

需要防止另一种偏差：只有发生回踩的订单块才进入交易分析，而没有回踩的订单块全部被忽略。对于交易策略，这种筛选可以是合理的，但在研究订单块本身的预测能力时，必须明确样本定义和条件，否则结论容易被选择偏差扭曲。

## 7.4 第四层：衡量增量收益是否稳定

我建议重点跟踪以下指标。

**增量净收益：**

 $\Delta R=R_B-R_A$

其中  $R_A$  和  $R_B$  是相同样本外区间的净收益率。

**增量 Sharpe：**

 $\Delta S=S_B-S_A$

但 Sharpe 的差值不能直接视为统计显著性证明。还需要考虑两个模型收益序列的相关性及估计误差。

**回撤改善：**

 $\Delta DD=DD_A-DD_B$

这里的  $DD$  指最大回撤的绝对百分比。例如，模型 A 回撤 12%，模型 B 回撤 10%，则回撤改善为 2 个百分点。

此外，还应统计：

- 增量净收益在多少个样本外窗口中为正。
- 增量收益是否集中于某一个品种或某一年。
- 交易成本增加后，增量收益是否仍然存在。
- 参数轻微变化后，增量效益是否消失。
- 订单块是否改善了极端亏损，而不只是提高了胜率。

**我更看重跨时间、跨品种的稳定性，而不是某个参数组合下最高的 Sharpe。**

# 八、第七步：采用滚动样本外验证，而不是一次性切分历史数据

如果你把 2018—2025 年的全部数据用于寻找最优参数，再用同一段数据报告收益，那么结果很容易过度乐观。

建议将回测流程分成四个阶段。

## 8.1 历史数据切分

例如，假设有 2015—2025 年的完整历史数据：

| 阶段 | 示例区间 | 用途 |
| --- | --- | --- |
| 开发集 | 2015—2020 | 研究订单块定义、调试程序 |
| 验证集 | 2021—2022 | 选择参数及过滤条件 |
| 样本外测试集 | 2023—2024 | 检验策略是否泛化 |
| 前瞻验证 | 2025 年及以后 | 模拟新数据下的实际运行 |

这些年份仅用于说明方法，实际区间应根据你拥有的数据、品种上市时间和市场制度变化确定。

不能因为某段样本外结果不好，就不断修改参数，再把同一段数据重新称为样本外测试集。

一旦它参与了策略选择，就不再是严格意义上的未见数据。

## 8.2 滚动前推

比固定切分更进一步，可以采用 Walk-forward：

1. 使用过去一段历史数据选择参数。
2. 在随后一个季度或半年内固定参数运行。
3. 记录该窗口的样本外绩效。
4. 将窗口向前移动。
5. 使用新的训练窗口重新选择参数。
6. 汇总所有未参与当期训练的收益。

参数更新频率必须预先确定，不能在策略表现差时临时提前调参。

可以参考 VectorBT 的滚动前推和时间序列交叉验证说明

，其中介绍了滚动窗口、扩展窗口和样本外测试的实现思路。

## 8.3 参数稳定性测试

不要只搜索一个最优参数点。

例如，订单块回看窗口可以测试：

 $N\in\{3,5,8,10,15\}$

ATR 止损系数可以测试：

 $k\in\{0.5,0.75,1.0,1.25,1.5\}$

趋势过滤也可以使用不同的均线窗口。

但我不建议一开始就对所有参数进行完整的笛卡尔积搜索，因为参数组合数量会迅速膨胀，增加过拟合风险。

更合理的顺序是：

1. 先验证订单块定义。
2. 再验证趋势过滤。
3. 然后验证动量。
4. 再验证止损参数。
5. 最后只对少量合理候选模型做联合优化。

如果某个策略只有在参数精确等于某个数值时才表现良好，周围参数稍微变化就失效，那么它的可靠性值得怀疑。

## 8.4 多品种验证

对你的国内商品 CTA 研究台，可以先选择具有不同市场特征的品种开展测试，例如：

- 棉花：研究订单块在农产品趋势和季节性行情中的表现。
- 甲醇：研究订单块在能源化工、产业链和宏观事件驱动行情中的表现。
- 白糖：研究订单块在农产品供需切换及趋势行情中的表现。
- 其他流动性较好的商品：验证策略能否跨品种泛化。

品种选择应考虑历史数据完整性、流动性、交易成本和合约规则。

不要先挑选历史上表现最好的几个品种，再声称策略适用于整个商品市场。

### 为什么要这样拆分？

**第一，订单块识别器必须可以独立测试。**

你可以直接检查每一个订单块的形成时间、确认时间、区域上下沿及失效时间。

**第二，执行引擎必须支持多个模型共用。**

否则，订单块模型可能使用更乐观的成交规则，而趋势基准模型使用更保守的成交规则，比较就失去了意义。

**第三，评估模块应当独立于策略。**

同一套指标计算程序可以评估订单块、唐奇安突破、均线趋势、均值回归等策略，减少重复开发和统计口径不一致的问题。

**第四，实验必须可以复现。**

每次运行都应记录数据版本、代码提交、参数、成本模型、回测区间和随机种子。只有这样，后续才知道某次绩效变化是策略改进，还是数据或代码发生了变化。

## 9.1 技术选型

第一阶段不需要急于搭建复杂的高性能系统。

| 组件 | 建议 | 原因 |
| --- | --- | --- |
| 数据处理 | pandas、NumPy | 适合历史行情处理和指标计算 |
| 指标计算 | 自建模块 | 明确控制时间对齐和未来函数 |
| 回测引擎 | 先使用现有引擎；没有时评估 VectorBT 或 Backtrader | 避免重复造轮子 |
| 复杂成交模拟 | 自建事件驱动执行模块 | 处理订单状态、限价单和持仓约束 |
| 统计分析 | pandas、SciPy 等 | 评估收益分布及统计可靠性 |
| 实验记录 | CSV + JSON + Git | 低成本实现可追溯研究 |
| 可视化 | Matplotlib、Plotly | 观察净值、回撤、订单块和交易分布 |

如果你的目标是快速比较大量指标组合，VectorBT 值得优先评估；如果需要更灵活地控制订单生命周期、成交和持仓状态，可以评估 Backtrader 或现有自建引擎。

不要为了采用某个框架而重写已经成熟的执行系统。先检查 `cta-path-a` 现有代码，确定它缺少的是信号识别、回测执行，还是实验管理，再决定是否引入新依赖。

# 十、第九步：先写一个可测试的回测主流程

在正式开发前，建议先把模型接口和交易流程确定下来。

下面是接近实际工程的伪代码，重点展示模块之间的关系。它不是可直接运行的完整回测程序，也没有使用真实行情计算任何收益。

```
def run_experiment(data, config):
    # 1. 数据检查
    data = validate_ohlcv(data)

    # 2. 计算技术指标
    features = calculate_features(
        data,
        trend_config=config.trend,
        momentum_config=config.momentum,
        atr_config=config.atr,
    )

    # 3. 生成订单块事件
    order_blocks = detect_order_blocks(
        data=data,
        structure_config=config.structure,
    )

    # 4. 只保留当时已经确认、可以使用的订单块
    order_blocks = enforce_event_timestamps(
        order_blocks,
        data.index,
    )

    # 5. 生成候选交易信号
    signals = generate_signals(
        data=data,
        features=features,
        order_blocks=order_blocks,
        config=config,
    )

    # 6. 将信号交给独立执行引擎
    # 包含成交、手续费、滑点、止损、止盈和持仓管理
    trades = simulate_execution(
        data=data,
        signals=signals,
        execution_config=config.execution,
        cost_config=config.costs,
        risk_config=config.risk,
    )

    # 7. 计算净值、风险和交易质量
    metrics = evaluate_performance(
        trades=trades,
        data=data,
        config=config,
    )

    # 8. 保存实验信息，确保可以复现
    save_experiment(
        config=config,
        trades=trades,
        metrics=metrics,
    )

    return {
        "trades": trades,
        "metrics": metrics,
    }
```

这里有两个需要特别注意的地方。

第一，`enforce_event_timestamps()` 不应只是检查时间戳，还应验证订单块的所有输入信息在对应时间是否已经可知。

第二，`simulate_execution()` 必须模拟真实可执行的交易路径，不能直接根据收盘价上的买卖信号计算理想化收益。

如果现有项目已经有回测引擎，就应优先复用它，而不是复制一套新的模拟逻辑。

# 十一、第十步：建立自动化模型对比报告

每次实验结束后，自动生成一张汇总表。

建议至少包含以下字段：

| 字段 | 含义 |
| --- | --- |
| experiment_id | 实验唯一编号 |
| model_name | 模型名称 |
| data_version | 行情数据版本 |
| code_commit | Git 提交版本 |
| parameter_hash | 参数配置哈希 |
| sample_period | 回测区间 |
| trade_count | 交易次数 |
| annual_return | 年化净收益 |
| max_drawdown | 最大回撤 |
| sharpe | Sharpe Ratio |
| sortino | Sortino Ratio |
| profit_factor | 盈利总额与亏损总额绝对值之比 |
| expectancy | 单笔净期望收益 |
| total_cost | 总交易成本 |
| turnover | 换手率 |
| out_of_sample_return | 样本外收益 |
| robustness_score | 稳健性评价 |
| incremental_return | 相对基准的收益变化 |

其中，`robustness_score` 不建议直接把多个指标加权后得到一个看似精确的数字。初期更适合采用独立的稳健性检查清单，避免一个任意设定的综合分数掩盖策略缺陷。

还可以为每个模型生成三张关键图表：

1. **净值与回撤图：** 比较模型在不同市场阶段的收益路径。
2. **参数稳定性热力图：** 观察相邻参数组合的表现是否一致。
3. **增量效益图：** 显示增加订单块后，各样本外窗口的收益变化。

这三张图通常比单独展示一条漂亮的净值曲线更有研究价值。

# 十二、第十一步：设置模型晋级标准

建议采用分阶段晋级机制，避免一个偶然表现良好的模型直接进入实盘。

## 阶段 A：程序正确性

必须全部通过：

- 无未来函数。
- 无信号时间穿越。
- 无不可能的成交价格。
- 手续费和滑点正确计入。
- 止损及跳空处理符合预定规则。
- 合约乘数和换月处理正确。
- 同一实验能够重复运行并得到一致结果。

任何一项失败，都不进入绩效评价。

## 阶段 B：基础策略有效性

检查：

- 扣除成本后，样本外期望收益是否为正。
- 收益是否依赖极少数交易。
- 最大回撤是否可接受。
- 不同年份的表现是否过度集中。
- 交易成本提高后，策略是否仍有合理的收益空间。

不必要求每个年份都盈利，但必须理解亏损阶段来自什么市场状态，以及策略是否具备可控的失效边界。

## 阶段 C：增量价值验证

订单块模块需要证明至少一项明确优势：

- 提高风险匹配后的净收益。
- 改善风险调整后收益。
- 降低回撤或极端亏损。
- 降低无效交易和交易成本。
- 改善不同市场状态下的适应性。

如果订单块没有提供稳定的独立贡献，就不应该因为它在图表上看起来更符合交易逻辑而保留它。

## 阶段 D：前瞻验证

在模型冻结后：

1. 使用固定参数生成信号。
2. 记录每个订单块的形成、回踩、入场和失效。
3. 对比模拟成交与实际可成交价格。
4. 持续记录滑点、手续费和信号偏差。
5. 定期检查模型是否偏离历史预期。

前瞻验证应先以模拟交易为主。只有在数据、执行和风险控制均得到充分验证后，才考虑小规模实盘。

>
